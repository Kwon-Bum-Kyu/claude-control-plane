# PRD Template — CCP 제품 요구사항 문서 템플릿

CCP 플러그인의 PRD 작성 시 따라야 할 섹션 구조와 작성 원칙.

## 필수 섹션

### 1. 목표 (Goal)
한 문장. "{누가} {무엇을} 함으로써 {어떤 가치}를 얻는다" 형식.

### 2. 사용자 페르소나
보고서 §6.1 (한국 개인 Pro 사용자)을 1차 페르소나로 고정. 부 페르소나는 §6.2~6.5에서 선택.

### 3. 범위 (Scope)
| 구분 | 항목 |
|------|------|
| In Scope (MVP) | 4개 핵심 항목 (project_brief.md 참조) |
| Out of Scope (Phase 6+) | scope-guard가 백로그로 분리한 항목 목록 |

### 4. 사용자 시나리오
ux-designer가 작성한 시나리오를 인용. 최소 3개:
- 신규 사용자: 설치 → 첫 호출
- 숙련 사용자: 라우터 우회, 직접 슬래시
- 실패 복구: OAuth 만료, Antigravity CLI 미설치

### 5. 기능 요구사항
슬래시별·서브에이전트별 동작 명세. 상세는 `01_command_spec.md`, `01_subagent_spec.md`로 분리하고 PRD는 요약만.

### 6. 비기능 요구사항
| 항목 | 기준 |
|------|------|
| 토큰 절감 | 동일 워크로드 대비 15%+ |
| 라우터 정확도 | 80%+ |
| 첫 호출 성공률 | 5분 내 90%+ |
| 공개 안전성 | 비밀 정보 노출 0건 |

### 7. 합격 기준 (Acceptance Criteria)
모든 비기능 요구사항이 측정 가능한 형태로 변환. token-economist의 시나리오 ID(T1~T5)와 매핑.

### 8. 리스크 카탈로그
보고서 §5의 R1~R6를 그대로 인용. 각 리스크에 완화 책임자(에이전트 이름) 명시.

### 9. 미결 사항 (Open Questions)
결정되지 않은 항목 목록. 빈 섹션이라도 명시적으로 둘 것.

## 작성 원칙

- **한 명세 = 한 검증 가능한 문장**. "사용자 친화적" 같은 모호한 표현 금지
- **모든 수치는 출처 명시**. 보고서 인용은 §번호 표기
- **자체 결정 금지**. 기획 팀 합의 없이 독단으로 결정한 항목은 `## 미결 사항`으로 이동
- **omc 30~50% 광고 수치는 절대 인용 금지** (보고서 §5에서 검증 불가)

## Why

PRD는 검수·개발 Phase의 단일 진실 소스(Single Source of Truth)다. 모호한 PRD는 검수에서 잡지 못한 결함을 개발에서 폭발시킨다. 측정 가능한 합격 기준이 PRD에 없으면 token-economist의 시나리오가 공중에 뜬다.
