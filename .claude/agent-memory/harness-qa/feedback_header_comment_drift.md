`plugin-scaffolder`가 작성한 셸 스크립트에서, 파일 상단의 설계 의도 주석(예: "disable → worktree/patch → validate → marketplace add → install → verify 순서로 실행해 disable 창을 최소화한다")이 실제 코드가 구현한 순서와 다를 수 있다. 발견 사례: `install.sh` 헤더는 "disable 다음 worktree/patch"라고 쓰여 있었지만, 실제 코드는 B-1(신선도 검증) → I-0(worktree/patch, 멱등·실환경 무변경) → B-2(disable) 순서였다 — 이는 오히려 disable 창을 더 짧게 만드는 **더 안전한** 구현이었고 기능 결함은 아니었지만, 주석과 코드가 어긋난 것 자체는 문서 결함(경미)이다.

**Why:** incremental QA의 핵심은 "존재 확인이 아니라 동작 검증"이며 경계면 교차 비교다. 헤더 주석은 리뷰어가 가장 먼저 신뢰하는 문서이므로, 실제 실행 순서와 다르면 향후 유지보수자가 주석만 보고 잘못된 멘탈 모델을 가질 위험이 있다. 이번 케이스는 다행히 코드가 주석보다 안전한 방향으로 벗어난 경우였지만, 반대 방향(코드가 주석보다 위험한 순서)이었다면 치명 결함이 됐을 조합이다.

**How to apply:** 원자적 시퀀스를 구현한 스크립트를 검증할 때는 (1) 파일 헤더의 서술적 순서와 (2) 실제 코드에 나타나는 단계별 실행 순서를 각각 별도로 추출해 대조한다. 일치하지 않으면 어느 쪽이 실제로 더 안전한지 판단한 뒤(코드가 안전하면 "경미: 주석 갱신 권고", 코드가 위험하면 "치명: 즉시 수정 요구") 심각도를 부여한다. 관련: [[project-e2e-run-20260821]].
