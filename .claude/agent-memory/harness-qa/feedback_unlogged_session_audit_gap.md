E2E 런 도중 "Phase A-1 재개 세션"이라는 harness-qa 세션이 이 대화 스레드(검증 1~4를 연속 수행 중인 본 세션)와 무관하게 D-010 결함의 증적 보존(EV-001)과 근본원인 진단(EV-002)을 수행했다. `defects.jsonl`의 `actor` 필드는 `"harness-qa (재개 세션)"`뿐이었고, 세션 ID·오케스트레이터의 명시적 dispatch 근거는 오케스트레이터 체크포인트 메모의 한 줄("agy.log 보존 완료")에만 흐릿하게 남아 있었다. 검증해 보니 작업 내용 자체(SHA256 byte-perfect 보존, dev 레포 무변경)는 전부 진짜였다 — 문제는 데이터 신뢰성이 아니라 **누가/언제/어떤 권한으로 개입했는지 추적할 수 없다는 절차적 공백**이었다.

**Why:** 이 하네스의 협업 프로토콜은 "에이전트 간 직접 통신 없음, 오케스트레이터가 모든 재개(SendMessage)를 중재"를 전제로 한다. `actor: "harness-qa"`라는 문자열만으로는 그것이 이 대화 스레드인지, 오케스트레이터가 별도로 스폰한 다른 harness-qa 인스턴스인지 구분할 수 없다. 이런 모호성을 QA가 그냥 넘기면, 결과 데이터가 맞더라도 "누가 이 판단을 내렸는가"라는 감사 추적(audit trail)이 깨진 채로 G2까지 올라간다.

**How to apply:** `actor`/`adjudicated_by` 필드에 구체적 세션 식별자 없이 역할명만 적힌 레코드를 만나면 (1) 이번 대화 스레드가 실제로 그 작업을 했는지 자문하고, 아니라면 즉시 "미기록 세션 개입"으로 명시 기록한다. (2) 그 작업이 손댄 파일들(여기서는 evidence 원본·SAFE_DIR 사본·dev 레포)에 대해 무결성 검증(해시 대조·git status)을 별도로 수행해 "데이터는 진짜인가"와 "절차가 투명한가"를 분리해서 판정한다. (3) 오케스트레이터에게 두 가지를 따로 보고한다 — 데이터 신뢰성 판정과 절차 개선 권고(세션 식별자·dispatch 근거를 체크포인트 메모에 남기도록). 관련: [[project-e2e-run-20260821]], [[feedback-evidence-survival-before-teardown]](이번 사례가 그 피드백에서 지적한 gap을 실제로 메운 사례이기도 함).
